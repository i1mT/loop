# dev 预览与 main 生产交付进度

代码已实现并通过本地验收。一次性 GitHub 和 GitLab 项目的真实部署验收待执行。

## 目标

**排队 → 技术方案 → 开发 → 合并 dev 部署预览环境 → 在预览环境测试 → 发布生产（人工点合并按钮）→ 生产环境回归测试**

预览环境就是测试环境。开发完成后，任务自动进入 dev，智能体跑完预览测试，Loop 自动准备 `dev → main` PR/MR。用户在 Loop 点合并后，由仓库的 main 流水线部署，原智能体再做生产回归。

## 完成条件

- 任务详情展示七个节点。技术方案沿用原有审核设置。任务合入 dev 和预览部署、测试自动推进，生产合并由用户点击触发。
- 项目设置可以填写、查看和修改两套环境的 URL、测试账号和密码。专用测试凭证明文保存，在对应测试节点直接随消息交给原智能体。仓库 `AGENTS.md` 可以说明怎么测和什么算通过。
- GitHub Actions 与 GitLab CI 都能按分支和提交查询流水线。对应流水线成功结束即视为部署完成，并开始环境测试。失败、取消和查不到运行记录各自可见，有明确的继续方式。
- 同一仓库共用一个打开的 `dev → main` 生产 PR/MR，允许一起发布 dev 上的其他任务。点击合并时展示待合入提交和已知包含的任务，合并后记录实际版本。每个任务的测试结果分别记录。
- 生产流水线成功后自动触发原智能体回归。回归通过后任务才完成，回归失败时保留生产已部署的事实和失败详情。
- GitHub 和 GitLab 都有覆盖七节点、失败重试、并发和重启恢复的验证。旧任务和已合并记录仍可查看，进行中的旧任务按原流程收尾。

## 当前基线

- `packages/core/src/task-states.ts` 定义状态转换。`apps/web/lib/status.ts` 和任务页展示排队、开发、审核、发布四步。`apps/web/lib/daemon-api.ts` 通过 `reportHead`、`approveTask`、`recordMerge`、`completePublish` 将一条 PR/MR 和一次发布串联。
- 任务的开发起点和 PR/MR 目标都使用项目的 `main_ref`。`apps/daemon/src/serve.ts` 的原发布任务在合并后调用 `publishPrompt`，要求智能体按仓库文档部署生产。`apps/daemon/src/forge.ts` 已支持 GitHub 与 GitLab 的 PR/MR 操作和按审核提交合并，目前缺少流水线查询。
- `apps/web/lib/task-plan/service.ts` 目前通过启用的飞书绑定初始化技术方案记录。可以复用现有文档、版本、审核和会话恢复逻辑，让无飞书绑定的项目也能在 Loop 内保存和查看方案。

## 核心决策

- 新流程固定 `dev → 预览环境` 和 `main → 生产环境`。接入项目在对应分支更新时运行部署流水线。
- 流水线状态由 daemon 用已有的 GitHub CLI 或 GitLab API 凭证查询。GitHub 按配置的部署 workflow、目标分支和提交筛选，GitLab 按目标分支、提交及 `push` 来源查询分支 pipeline。
- 现有任务轮次固定各自执行流程。老项目填好环境设置后，新轮次进入七节点流程，旧轮次按原路径收尾。技术方案依然可按现有设置审核，生产合并始终由用户点击。
- 生产发布记录保留一个共享 PR/MR 及实际包含的任务轮次。某个任务的预览通过即可准备 PR/MR，生产版本允许带上其余 dev 改动。每个任务单独记录自己的预览与生产测试结果。
- 已有分支或环境配置变更时，按真实部署版本更新界面。测试账号为项目自备的专用账号，项目有权限的用户可以查看并编辑明文，测试时直接传给智能体。

## 风险与处理

| 情况 | 处理 |
| --- | --- |
| 分支流水线延迟创建、失败、取消或 API 暂不可用 | 先区分等待、明确失败和暂时读不到，再按阶段 02 的记录恢复查询 |
| 共享环境在测试期间部署了更新版本 | 将测试结果绑定实际验证的版本，按对应最新部署继续，旧结果保留在记录里 |
| 用户点合并时 dev 已变化 | 合并接口以用户看到的提交为准，刷新生产 PR/MR 后重新点合并 |
| 合并成功后 daemon 中断 | 从托管平台和已记录的 PR/MR 查回提交，续跑流水线查询和测试 |
