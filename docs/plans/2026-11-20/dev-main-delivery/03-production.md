# 阶段 03 · 生产发布与回归

## 阶段目标

阶段 02 通过后，Loop 在预览测试通过时自动准备共享生产 PR/MR。用户在 Loop 点击合并，main 的部署流水线成功后，原智能体完成生产回归。

## 设计与实施

- 以仓库为单位查找或创建 `dev → main` 的开放 PR/MR，按源、目标分支和仓库匹配，复用已有 PR/MR。保存一个共享生产发布记录，关联实际包含的任务轮次。任一任务预览通过后即可准备生产 PR/MR，允许同批带入 dev 上的其他任务。
- 生产节点展示 PR/MR、当前 dev 提交和已知包含的任务。由用户在 Loop 点击合并，权限沿用已有任务审核权限。daemon 按点击时对应的提交调用托管平台合并接口，目标分支是 main。期间 dev 有更新则刷新待合入信息并要求重新点击。两位用户同时点击时复用同一个合并操作。
- 保存实际 main 合并提交，复用阶段 02 的流水线查询，等待对应生产流水线成功。配置和仓库接入指南需说明 main 更新自动部署生产。复用现有会话推进方式，将生产 URL、测试账号和密码直接发给对应任务的原智能体，按项目规范执行回归并记录结果。
- 共享发布仍逐任务记录测试。被一起合入 main 的任务可看到所属生产批次和部署结果，保留其真实预览测试状态，并在生产部署成功后执行各自的回归。回归失败保留已部署记录，支持在对应生产版本上重试。修复代码按同一流程重新从 dev 走一轮。
- 用一次性 GitHub 和 GitLab 仓库完成端到端验收。更新 README 的接入规则、架构和任务契约，保留现有兼容路径直到正在进行的旧轮次收尾。

## 测试方案

用 A、B 两个任务覆盖同一个生产 PR/MR、合并前 dev 前进、重复点击、合并成功后重启、生产流水线失败和回归失败。验证属于别的 main 提交的流水线成功不会推进本批。用合成数据查看 900px 和 1440px 的节点状态、待发布版本和人工按钮，运行 `pnpm run typecheck`、相关测试和 `pnpm run build`。

## 完成门禁

GitHub 和 GitLab 均有七节点端到端记录，生产 MR/PR 由 Loop 自动准备，main 只有在用户点击合并后才由 Loop 更新。生产部署成功与回归结果都可见，同一批包含的任务可分别查看各自的测试结论。兼容迁移和中断恢复有测试证据。
