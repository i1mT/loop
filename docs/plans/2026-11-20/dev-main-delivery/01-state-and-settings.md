# 阶段 01 · 状态与项目设置

## 阶段目标

建立七个任务节点和项目环境设置，让技术方案能在 Loop 内独立流转，并保留旧任务的历史与恢复路径。实际合并与部署查询由后续阶段接入。

## 设计与实施

- 使用 `packages/core/src/task-states.ts` 定义状态转换，在 `apps/web/lib/status.ts` 统一映射到七个节点，再更新任务卡、审核入口、通知和 SDK。开发结束只进入预览部署。预览测试通过才准备生产审核，生产合并和流水线成功后才进入回归，回归通过后才完成任务。
- 复用 `apps/web/lib/task-plan/` 的按轮次和版本保存方案、审批与恢复机制。无飞书绑定时，保存方案到 Loop 后按现有审核设置流转。绑定飞书的空间继续同步 Wiki。技术方案审核绑定具体版本，修订后要求重新确认。
- 在现有项目设置页增加预览和生产两组 URL、测试账号、密码。复用管理员和项目权限，授权用户可填写、查看和修改完整值，使用普通字段明文保存。账号密码按项目实际需要填写，可留空。GitHub 项目另填写对应两套环境的部署 workflow，GitLab 使用对应分支的 pipeline。
- 用现有迁移序列新增字段，保留 `main_ref` 和旧 PR/MR 记录供旧轮次使用。新流程固定使用 `dev` 和 `main`，配置齐备后只对新任务轮次生效。已有任务通过轮次所绑定的流程版本恢复。
- 环境信息存在项目设置中，任务只记录测试对应的环境、提交、流水线和测试结果。原智能体收到对应环境的 URL 和测试账号密码，在测试节点按项目文档执行。

## 测试方案

验证状态机的正常路径和不可跳过的生产确认，测试未接飞书与已接飞书的方案流转。通过旧数据库升级测试验证正在运行和已结束的任务。用合成项目验证环境字段填写、查看、修改及项目访问权限，并查看任务页和设置页在 900px、1440px 下的展示。

## 完成门禁

旧任务仍能恢复，新任务可保存两套环境设置并进入开发。无飞书项目可保存并查看技术方案，启用方案审核时仍需批准当前版本。状态测试覆盖所有七个节点。
