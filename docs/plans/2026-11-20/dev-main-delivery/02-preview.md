# 阶段 02 · 预览部署与测试

## 阶段目标

阶段 01 通过后，智能体完成开发和项目检查，Loop 自动将任务合入 dev。预览部署成功后，原智能体使用对应环境的链接和账号完成测试。

## 设计与实施

- 沿用独立任务 worktree、`publishBranch` 和 `syncAndMerge`，基于 `origin/dev` 创建任务 `→ dev` 的 PR/MR。项目检查通过后由 Loop 自动合入。并发导致 dev 前进时，同步后重新跑适用检查。真实冲突交给原会话修复并更新原 PR/MR。
- 在 `apps/daemon/src/forge.ts` 扩展分支流水线查询。GitHub 匹配 `push`、分支、提交和配置的 workflow。GitLab 匹配 `push`、分支和提交。用实际合并后的 dev 提交查找部署运行，保存提交、运行 ID、链接和状态。成功终态表示部署完成，失败、取消、跳过、等待创建和查询错误分别显示。暂时查不到时继续等待并可重新查询。
- 流水线确认成功后，向原会话直接发送预览 URL、测试账号和密码，要求按仓库 `AGENTS.md` 及其引用文档测试，并返回结论。测试结果记录实际验证的提交。若共享环境切到新版本，从成功的 dev 流水线确认该版本仍包含任务的合并提交，再继续测试。
- 验证失败时交回原会话修复。新改动从最新 dev 进入新的任务 PR/MR，完成新部署和验证。恢复时按任务轮次、租约和提交从最近的合并或流水线记录续跑。

## 测试方案

测试同分支的其他提交、同提交的其他 workflow、延迟创建、失败重跑、部署被新版本替换和 API 临时不可用。使用一次性仓库和模拟智能体覆盖并发合并、冲突修复及 daemon 重启。进入预览测试时断言智能体收到正确环境的测试账号和链接。

## 完成门禁

两种托管平台的测试证明任务可自动合入 dev，只有归属于本次部署的分支流水线成功后才开始测试。重启或重试复用原会话和既有 PR/MR，测试失败不能产出通过记录。
